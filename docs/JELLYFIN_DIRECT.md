# Jellyfin 分机媒体直出

本功能包含在正式版 `v0.9.8-relay.2`。历史 `v0.9.8-relay.2-rc.1` 不包含此功能，不能只更新配置而继续使用旧镜像。本指南使用默认 `/app/fntv-proxy` 入口；三服务合并和独立密钥隔离见 [统一指南](UNIFIED.md)，两套配置不同。已完成现场客户端 STRM 实播，不代表所有 Jellyfin 客户端均完成验证。

NAS 上的 Jellyfin 负责登录、媒体库和播放授权，主代理签发限时地址；机房媒体节点读取源站并直接向客户端传输视频。机房节点不需要挂载 STRM 目录。

```text
登录、选片、授权：客户端 → NAS Jellyfin 主代理 → Jellyfin
符合条件的视频：客户端 → 机房媒体服务 → 机房源站
```

## 模式与限制

| 配置 | 行为 |
| --- | --- |
| `jellyfin.enabled: false`（默认） | 不启动 Jellyfin 代理。 |
| `jellyfin.delivery_mode: redirect`（默认） | 源站 302 模式，要求客户端能直接访问源站。 |
| `jellyfin.delivery_mode: direct` | 对符合条件的 STRM/远程媒体静态播放签发机房媒体地址。 |

`jellyfin` 与 `emby` 配置块独立；顶层 `delivery_mode`、`stream_mode` 仍控制飞牛影视，不会代替 Jellyfin 的模式开关。同一进程同时启用 Emby 和 Jellyfin 时，两者使用同一顶层 `media` 签发密钥及媒体地址；需要独立媒体端口与密钥时，必须像本示例一样另起主代理进程。此功能不会自动修改媒体库路径或将已挂载的视频文件转换为 STRM。

本地文件、转码、直播/HLS、字幕和图片等仍按 Jellyfin 原流程处理。客户端不能直接播放原格式时，回退转码仍可能使视频经过 NAS；机房媒体节点不承担转码。成功播放不等于成功直出，必须核对实际数据流。

播放信息中的 `DirectStreamUrl` 使用主代理上的相对入口，再由该入口 `302` 到机房签名地址。这个跳转只传输控制信息，不通过主代理搬运视频。不要手动替换成完整机房 URL，以免客户端再次拼接服务器地址。

## 1. NAS 主代理

使用 [Compose 示例](../deploy/jellyfin-direct-proxy/compose.yaml) 和 [配置示例](../deploy/jellyfin-direct-proxy/config.yaml.example)。在仓库 `deploy/jellyfin-direct-proxy` 目录复制并修改配置：

```sh
cp config.yaml.example config.yaml
# 完成下面的地址、挂载和密钥配置后启动
docker compose pull
docker compose up -d --no-build
```

示例测试入口为 `http://192.0.2.10:18096`，后端为 `http://127.0.0.1:8096`。应按实际主机修改，并先确认端口空闲。原 Jellyfin 入口保留不动；客户端连接主代理而不是媒体端口。示例禁用 Emby，未使用的飞牛监听仅绑定 `127.0.0.1:28007`。

Compose 左侧 `/replace/with/host/strm` 必须换成真实 STRM 宿主机目录；右侧路径必须与 Jellyfin 返回的 `.strm` 文件绝对路径一致，并包含在 `allowed_strm_roots` 中。例如返回 `/media/strm/电影/a.strm`，就将挂载右侧与白名单同时改为 `/media/strm`。只读挂载即可，不需要改写 STRM 文件。目录越界和符号链接越界会被拒绝。

**既有库路径不能靠代理配置自动切换。** 若媒体库返回 `/media/...` 下的 `File` 视频而不是 `.strm`，不能作为 STRM 直出验收样本。应先检查实际播放信息，必要时另建小型 STRM 测试库并完成扫描，保留原库不动。`strm_path_map` 只改写 STRM 内容中的源 URL，不修复媒体库或文件系统路径。

将 `allowed_upstreams` 改为真实源站的 `host:port`。将 `media.public_base_url` 改成客户端可达的媒体节点 HTTPS 地址。将同一密钥安全放到 NAS 和机房媒体节点各自的 `./secrets/media_key`，文件权限设为 `0600`；内容为 64 位十六进制文本，不能提交到 Git，也不能两端分别自动生成。

NAS 采用 `role: proxy`，不启动媒体监听，不需要媒体 TLS 证书。示例 HTTP 登录入口仅适用于可信内网测试，公网正式入口应配置 HTTPS，不能直接暴露明文测试端口。

## 2. 机房媒体节点

推荐 Jellyfin 使用独立媒体容器、端口和密钥，以便独立排错、升级和限制访问。参照 [分机部署指南](DIRECT_MEDIA.md) 及 [媒体节点配置](../deploy/direct/media.config.yaml.example) 创建 `role: media` 实例；源站应在机房就近访问，不能再经 NAS 取送视频。

本示例为 Jellyfin 预留 `49966`。请将媒体配置中的 `media.listen` 设为实际监听地址的 `:49966`，`media.public_base_url` 设为与主代理相同的 `https://media.example.com:49966`，两端配置同一密钥及所需源站白名单。复用部署模板时，同时检查 Compose 中的监听、端口发布和容器名称，不要覆盖已有飞牛影视或 Emby 容器。

路由器将公网 `49966` 映射到**机房媒体主机**的 `49966`，并允许相应防火墙流量。域名解析应指向机房公网出口，客户端到媒体节点不应再绕行 VPS。原有 `49963/49964/49965` 服务无需因此修改。这里的端口只是部署示例，不代表已为任何环境完成映射。

浏览器播放需要在媒体节点 `media.allowed_origins` 加入 Jellyfin 网页的精确 Origin，如内网测试的 `http://192.0.2.10:18096` 或正式 HTTPS 域名。Origin 包含协议、主机和非默认端口，不含路径；它不是访问鉴权的替代品，不应为了排错任意放宽。

通过 `media.tls_cert_file`、`media.tls_key_file` 指定有效证书完整链和私钥的容器内路径，并挂载整个证书目录。有效证书内容替换后支持热加载；路径改变需要重启。程序**不自动签发、续期或同步证书**。证书须匹配媒体域名且受客户端信任，客户端不需要配置共享密钥。使用 IP 也必须有匹配该 IP 的受信任证书，不能通过关闭证书校验解决。

技术上也可以复用已有媒体节点，但签发端必须共享其密钥，属于同一信任域，且需正确配置源站白名单和网页 Origin。独立部署能避免将不同服务的签发权限和故障影响范围混在一起。

## 3. 安全与验收

静态视频请求使用当前调用者凭据向 Jellyfin 核验播放授权，不能用其他用户的缓存获得权限。签发失败或源站不在白名单时拒绝请求，不回退泄露原始内网 URL。媒体节点还会校验回源重定向的目标地址。

签名地址本身是限时访问凭据，获得完整地址的人可在有效期内访问对应内容。`media.token_ttl_seconds` 默认 `3600`，范围 `1–86400` 秒；过期后重连、拖动可能需要重新取得播放地址。Jellyfin 撤销权限不等于已签发票据立即失效。不要公开密钥、登录凭据或完整播放 URL。

先让客户端连接独立测试入口，选择实际路径为 `.strm` 的已授权影片，验证起播和拖动；核对跳转终点为机房媒体地址、视频范围请求正常响应（通常为 `206`）、机房发送流量增长且 NAS 不传输同量级视频。仅接口返回 `302/206` 不足以代替真实客户端验收。

还应检查无效登录不能获得票据、无效或过期票据不能回源，以及本地文件或需要转码的内容仍遵循原 Jellyfin 流程。发现兼容问题时记录客户端版本和实际播放类型，不要将所有回退都归因于端口映射。

## 回退

测试阶段不切换原正式入口。停止独立测试 Compose 并让客户端连回原 Jellyfin 即可回退，不影响原 Jellyfin、Emby 或飞牛影视。仅恢复源站 302 模式时，改为 `jellyfin.delivery_mode: redirect` 并重建测试代理；该模式要求客户端直接可达源站。
