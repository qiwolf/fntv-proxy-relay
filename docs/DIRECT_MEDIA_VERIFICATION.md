# 专用媒体服务开发验证记录

本文保留早期开发阶段的历史验证记录，不作为当前版本的完整支持矩阵。正式版范围见 [v0.9.8-relay.2 发布说明](RELEASE_NOTES_v0.9.8-relay.2.md)。2026-09-29 后续已完成 Emby/Jellyfin 直出及三服务统一容器的现场 STRM 播放与机房流量核对；本文下方的“下一步”、未发布镜像与尚未实播等陈述仅指当时阶段。

开发验证：2026-09-28；现场补充：2026-09-29。开发分支：`codex/direct-media-server`。下述开发测试与现场验证分开记录，发布状态以 GitHub Release 和 Actions 为准。

## 已完成

- 旧配置默认 `role: proxy`、`delivery_mode: proxy`，保留旧 302 和同源 relay；独立 Emby 功能不切换媒体路径。
- 新增 proxy（签发端）、media（媒体端）、all（双监听）角色；通过 YAML 或 `FNTV_*` 环境变量选择。
- 跨进程 AES-256-GCM 限时加密票据；密钥不返回客户端，票据内媒体 URL 和凭据不以明文传输。
- 媒体端只处理有效票据的 GET、HEAD 和 CORS OPTIONS；正常未授权 HTTP 请求中止连接，不提供 UI。
- TLS、精确跨域来源、上游及重定向允许列表、Range、启动失败清理与停止双监听。
- 配置切换需重启；日志级别支持安全热重载，固定路径内的证书文件支持新握手自动热加载。播放地址改写失败不回退泄露原始 URL。
- 未提供手动密钥时，首次启动自动生成并持久化；旧文件损坏不覆盖。证书自动同步、自动申请和续期不在本次范围。

## 已执行验证

1. `go test -race -count=1 ./...`：通过，覆盖旧 relay/redirect、加密/过期/篡改/错误密钥、独立签发端与媒体端、真实双监听、TLS、Range/HEAD、跨域、启动冲突、关闭和日志热重载竞态。
2. `go vet ./...` 与 `git diff --check`：通过。
3. 三种部署示例均通过 Compose 配置解析；proxy/media/all YAML 示例均经真实配置加载测试，临时测试密钥文件权限为 0600。
4. Docker 本地构建 `fntv-proxy-relay:direct-local` 成功（本机 linux/arm64）。补齐热加载与自动密钥后的镜像 ID：`sha256:9f4da6bebafee6f74963d21f98471b448fabddef839b58909b6c260b256b08c1`。
5. 三个隔离网络临时容器实际启动：默认仅监听 28005；media 仅监听 49963；all 同时监听 28005 和 49963。媒体端根路径未授权请求无 HTTP 响应。测试容器随后停止并自动删除，没有对宿主机发布端口。
6. Linux amd64 静态二进制交叉编译成功；未声称已在 amd64 生产主机运行新版本。
7. 真实 TLS 握手验证同一监听器证书序列号切换；中途不匹配、缺失、损坏或过期的新文件不会替换旧有效证书；并发读取通过 race 检查。
8. 无密钥环境变量、无手动文件的隔离容器自动生成密钥：目录 0700、文件 0600。删除并重新创建容器、复用持久卷后，密钥摘要一致（没有打印密钥）。测试容器及专用测试卷均已清理。

## 现场验证补充（2026-09-29）

linux/amd64 飞牛主机已运行本次源码的 all/direct 版本，使用用户提供的可信证书及程序自动生成的持久化密钥。公网 TLS 校验成功，无票据请求断开。用户恢复既有 STRM 挂载后报告实际播放成功；只读检查确认挂载存在、播放地址改写日志、上游 206 响应，以及媒体端口连接累计发送量持续增长，容器无重启。

连接归属检查表明该次客户端流量经过用户的另一台网络代理节点，但已绕过原影视入口反代。完全直连验收需让客户端媒体域名走 DIRECT；不要把客户端网络代理误判为本服务回退中继。

这些结果不代表所有播放器、所有片源、长时间播放及并发压测通过。实际拖动尚未单独验收，Range 已有单元/集成与现场 206 证据。

## 未执行与下一步

继续验证不同客户端的跨域播放、实际拖动、长视频和并发带宽。开发阶段的容器检查和模拟媒体测试不能替代这些验收。

现有公网端口映射与 SNAT 不等于媒体服务已经上线。独立媒体服务放在家庭飞牛上时，仍消耗家庭与机房之间的隧道带宽；可使用同一镜像的 media 角色移到机房内独立主机。
